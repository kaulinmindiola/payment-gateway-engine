# ADR-0001: Manual Domain↔JPA Mapping in Adapters

## Status
Accepted

## Context
The domain (`domain/model/`, Phase 2) must remain free of framework annotations (`CS-03`, verified by ArchUnit). However, actual persistence (Phase 3) requires JPA entities (`@Entity`) with Hibernate's own annotations. Two approaches are possible: (a) directly annotate domain classes as JPA entities, or (b) maintain two separate models (pure domain + JPA entities) with explicit mapping between them.

Option (a) would directly violate `CS-03`. An intermediate alternative would be using an automatic mapping library (MapStruct) between both models.

## Decision
- Two completely separate models are maintained: `domain/model/*.java` (pure, no framework) and `infrastructure/adapter/persistence/entity/*Entity.java` (JPA annotated).
- Mapping between them is **manual and explicit**, implemented as private `toDomain()`/`toEntity()` methods inside each adapter (`JpaAccountRepositoryAdapter`, `JpaTransactionRepositoryAdapter`).
- MapStruct or any other automatic mapping library is not used.
- JPA entities reuse domain enums directly (`AccountStatus`, `TransactionStatus`, etc.) via `@Enumerated(EnumType.STRING)` — this does not violate the dependency rule: `infrastructure → domain` is the allowed direction by ArchUnit; the reverse is forbidden.
- Audit fields (`createdAt`/`updatedAt`) exist only in JPA entities (`@CreationTimestamp`/`@UpdateTimestamp`), never in the domain — the domain does not need to know when a row was persisted to decide on its own business invariants.
- To prevent a naive `save()` from overwriting `createdAt` with `null` on an update (client-assigned ID via `UUID.randomUUID()`, never DB-autogenerated), each adapter explicitly distinguishes creation from update: `findById()` locates the entity already managed by Hibernate and applies mutable changes via an `applyChangesFrom(...)` method (dirty checking), instead of rebuilding and persisting a new entity.

## Consequences
- The domain remains 100% free of framework annotations, automatically confirmed by `ArchitectureTest` on every build.
- Mapping is explicit and easy to reason/debug — no reflection "magic" or compile-time code generation.
- Cost: every new field in a domain class requires manually updating `toDomain()`/`toEntity()` in the corresponding adapter — this is intentional, not an oversight: it makes any drift between the domain model and the persistence schema visible in code review (`RISK-009`).
- The explicit create/update pattern (instead of `Persistable<UUID>`) adds an extra `SELECT` in the creation path, accepted because that route is not what `CS-01` measures (transfers between pre-existing accounts).

## Update (Phase 9): Transaction createdAt as Business Data
`Transaction.createdAt` is reclassified: the moment a payment occurs is business information (displayed, used to filter and sort history, `BR-015`), not a persistence metadata. It is generated by the domain in `createInternal`/`createExternal`, with the same precedent as `TransactionLog.createdAt` (Phase 2), truncated to microseconds to match `TIMESTAMPTZ` precision and guarantee the exact same value in the POST response, idempotent replay, and any GET request. `TransactionEntity` stops using `@CreationTimestamp` for that column. The rest of the original decision remains unchanged: `updatedAt` (all entities) and `createdAt` for `Account`/`User` remain metadata managed by Hibernate, outside the domain.
